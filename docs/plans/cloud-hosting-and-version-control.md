# 云端托管与版本管理方案

日期：2026-11-11。状态：产品方案；本文件中的版本中心、正式发布状态和分享密钥轮换尚待实施，不代表已部署。

## 当前部署目标：CloudBase

2026-11-11 起按 CloudBase 云托管推进部署；下文 CVM / Lighthouse 安装方式保留为原方案。当前尚未创建云端服务，也没有可交付的远程 MCP 地址。

已确认现有服务可以作为 Python 容器运行，启动命令为 `python -m dashboard_runtime server`，监听 `0.0.0.0:8000`，存活检查为 `/health`，客户端调用 `/mcp` 并使用 Bearer API Key。部署时明确设置服务端口与 `CHARTS_PORT=8000`，不能只依赖平台的 `PORT` 变量。

进入真实部署前还需完成：

1. 确认国内站或国际站、完整环境 ID 和地域；使用明确的环境 ID 查询云托管开通状态。
2. 提供具有部署权限的云端身份。CloudBase CLI 的环境凭据变量为 `CLOUDBASE_API_KEY` 与 `CLOUDBASE_ENV_ID`；它们与本服务的 `CHARTS_SERVER_TOKENS`、`CHARTS_SERVER_SECRET` 用途不同，不能互相替代。
3. 先适配持久化，再发布可保存业务数据的服务。现有草稿、历史和数据依赖本地 SQLite 文件；CloudBase 云托管实例的本地文件不能作为长期存储。`Store` 和传输存储使用 WAL，也不能直接把这些数据库挂到网络文件系统并开启多副本。需要将事务状态接入外部数据库，将独立业务文件接入对象存储；适配范围包含项目数据、版本历史及分享撤销状态。
4. 配置 HTTPS 对外地址、服务运行密钥与访问入口，再执行云端构建和启动检查。
5. 验证 API Key 拒绝未授权访问、MCP 初始化与工具发现、隔离项目中的读写，以及实例更换后的数据与历史保留。

COS 与 SCF 的分享、过期清理仍需分别部署和验收；启动 MCP 服务不代表这两项已完成。

部署依据：[CloudBase 官方入口](https://github.com/TencentCloudBase/cloudbase-skills/blob/main/skills/cloudbase/SKILL.md)、其中的 `cloudrun-development` 和 `cloudbase-cli` 指引，以及 [SQLite WAL 限制](https://sqlite.org/wal.html)。

## 产品入口

MCP、页面编辑器、项目资产和版本历史统一托管在腾讯云。客户端通过 HTTPS 调用远程 MCP，不再依赖用户电脑上的常驻 Python 进程。

原方案采用单台 Linux CVM 或 Lighthouse 运行现有 Docker 容器。项目数据库和数据文件挂载持久卷；COS 保存独立分享副本；SCF 执行到期删除。该方式保留当前 SQLite 和项目目录模型；切换 CloudBase 时按上节先适配持久化。

| 云端组成 | 内容 |
| --- | --- |
| CVM / Lighthouse | MCP HTTP 服务、页面编辑器、版本中心、分享访问网关 |
| 持久卷 | 项目配置、数据、草稿、已保存版本和发布记录 |
| 私有 COS | 只读分享网页、数据分片、访问控制和清理记录 |
| SCF | 每分钟执行到期、撤销和中断上传的物理清理 |
| 域名和 HTTPS | MCP 与网页的统一公开入口 |

现有部署入口见 [自托管服务器](../self-hosted-server.md)，COS 与 SCF 部署见 [腾讯云分享](../self-hosted-server.md#腾讯云在线分享与云端清理)。这是安装自有服务，不是将本地 stdio 配置直接上传到 COS。

## 两类访问密钥

| 类型 | 使用者 | 权限与管理 |
| --- | --- | --- |
| MCP API Key | Agent / MCP 客户端 | 高强度长令牌，经 `Authorization: Bearer` 请求头发送；不作为 URL 参数或页面密钥 |
| 页面分享密钥 | 分享接收者 | 8 位数字，仅访问对应分享；与分享配置绑定，云端保存加盐哈希 |

当前服务端已用 `CHARTS_SERVER_TOKENS` 或令牌文件支持 Bearer 令牌；接入客户端必须支持远程 HTTP MCP 和自定义请求头。首期这些令牌都是服务管理权限，不将它描述为已实现项目级权限、OAuth 或用户账号体系。

API Key 更新采用先同时接受新旧值、更新客户端、再撤销旧值的顺序。它与页面分享密钥独立，不能使用 8 位页面密钥连接管理接口，也不能把腾讯云 SecretId/SecretKey 发给 MCP 客户端。

分享密钥规则：

1. 每次新建分享生成独立密钥，不从全局部署环境读取固定页面密码。
2. 更新已有分享的目标版本或访问设置时，为该分享生成新密钥；也提供单独的“重新生成密钥”动作。
3. 轮换时递增分享授权代次。所有旧会话失效，每个文件请求都检查代次，不能只更新密码哈希。
4. 保存草稿、保存版本不轮换分享密钥。页面发布与“更新哪些分享”在发布确认中明确列出。
5. 新建分享不会自动撤销同一页面的其他独立分享。撤销或更新操作只作用于选定的分享。
6. 8 位数字密钥不可回读；遗失后生成新密钥。有效期由具体分享控制，支持不过期、7 天和 30 天。

## 保存与发布

| 对象/动作 | 作用 | 是否改变接收者正在访问的内容 |
| --- | --- | --- |
| 草稿 | 保存当前编辑进度与并发版本号 | 否 |
| 保存版本 | 完整校验后创建可命名、可预览、可比较的不可变版本 | 否 |
| 发布版本 | 指定一个已保存版本作为页面当前正式版本，记录发布事件 | 只有在同次发布中选定要更新的分享才改变这些分享 |
| 更新分享 | 将选定分享切到指定发布版本，更新有效期并轮换密钥 | 是；旧会话失效 |
| 恢复为草稿 | 将历史内容复制为新草稿，保留旧历史和当前发布状态 | 否 |
| 回退发布 | 把一个历史已保存版本作为新的发布事件，明确选定要更新的分享 | 是；完成后才替换对应线上内容 |

发布确认应列出版本、变更摘要、目标分享、有效期，以及密钥将轮换的影响。新产物完整上传并通过检查后再切换版本和授权代次；失败保留原发布内容及原有有效授权。不能先让旧分享失效，再开始上传新内容。

每个分享保存明确的发布版本及数据版本引用。编辑草稿或查看历史不能让分享悄悄切换数据。被版本历史引用的数据不因某个分享到期而删除；到期清理只删除该分享专属的远程副本和访问记录。

## 统一版本中心

页面顶部集中显示“保存版本”“发布”“版本与分享”。“版本与分享”打开同一侧栏；不再把恢复、发布状态和分享有效期分散在多个菜单中。

侧栏有“版本”和“分享”两个标签页，默认定位当前页面。

版本标签页：

- 按时间显示草稿、已保存版本和发布事件。
- 展示版本名称、时间、变更说明，以及“当前草稿”“已保存”“当前发布”等状态。
- 选择版本时先只读预览，不立即恢复；明确标识正在看历史内容。
- 提供命名、与当前版本比较、恢复为草稿、发布此版本。
- 区分“恢复编辑内容”和“回退线上发布”；前者不影响接收者。
- 没有编辑变化时不重复保存相同版本。保存、发布和恢复结果重新读取确认。

分享标签页：

- 列出分享名称或 ID、目标版本、有效期、访问状态和清理状态。
- 提供复制链接、新建分享、更新分享、重新生成密钥和撤销。
- 新生成的密钥仅在本次操作结果中展示；后续不提供明文查询。
- 已到期显示“已到期”；物理删除完成前显示“等待清理”或“清理重试中”。

## 与现有实现的差异

当前历史弹窗只显示版本编号/名称及恢复按钮。`checkpoint_meta.published` 仅用于防止历史清理，不表示当前线上发布版本。

实施时需要：

1. 把历史保护属性与发布状态分开；兼容保留既有受保护历史，不能把所有历史 `published=true` 都当成当前发布。
2. 增加明确的页面当前发布引用和独立发布记录；一个页面只能有一个当前正式版本。
3. 从历史读取指定版本，支持只读预览和比较，不必先覆盖当前草稿。
4. 恢复动作进入草稿；发布和更新分享是另外的明确动作。
5. 分享更新支持原子切换目标版本和授权代次，旧会话立即失效。
6. 统一 MCP、浏览器编辑器、版本中心与云端分享对状态的称呼和返回结果。

## 原 CVM / Lighthouse 安装顺序

1. 确定地域、已有或新建 Linux 实例、HTTPS 域名、私有 COS 桶及 SCF 执行角色。
2. 将本仓源码或构建镜像部署到实例；使用现有 `deploy/docker-compose.yml` 挂载 `/data` 持久卷。
3. 在部署环境配置 `CHARTS_PUBLIC_URL`、MCP API Key、COS 地域/桶/前缀和运行凭据。真实密钥不进入源码、页面或文档。
4. 按 `deploy/nginx.conf` 配置 HTTPS 和 Streamable HTTP 转发；MCP 请求不缓冲。
5. 部署 SCF 函数包、启用定时触发，并确认一次成功清理状态。
6. 有既有本地项目时显式迁移项目资产和数据，不能假设安装服务会自动上传本地看板。
7. 客户端改连统一 HTTPS `/mcp`，用 Bearer API Key 鉴权。远程 `projectRoot` 使用服务器项目名。
8. 验证创建/保存/发布/版本恢复、密钥轮换、过期清理和容器重启后的资产保留；退出本地 MCP 后复查云端访问与清理。

服务器端现有启动命令，在项目目录、部署环境和域名配置完成后执行：

```sh
docker compose -f deploy/docker-compose.yml up -d --build
```

## 实施顺序

先完成保存/发布状态分离和版本中心，再完成分享更新/密钥轮换；随后部署腾讯云并做真实云端验收。现有容器部署、Bearer 鉴权和静态分享能力可以复用，但不能把这些能力描述为已经实现上述完整版本管理。
