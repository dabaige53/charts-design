### 资源与费用边界

现有配置将最大实例数限制为 1，可作为试用起点；CPU、内存和副本数根据真实数据及导出任务的测量结果调整。最小实例为 0 允许空闲时缩容；持续连接及后台活动可能使服务继续处于活跃状态，需结合实际实例数和计量记录确认。

常规 ECharts 交互在浏览器中执行；服务端主要承担数据处理、版本读写、导出与分享资源传输。大数据导入/查询、Seaborn 渲染、并发导出和大量分享下载需要分别观察 CPU、内存、存储与流量。云端清理继续由独立 SCF 任务负责，不能依赖可能缩容到 0 的 MCP 服务执行。

云托管计算资源按 CPU、内存及实例运行情况计量；数据库、对象存储、流量、构建和日志按目标环境实际计费规则单独检查，包括实例数为零的时段。官方说明：[云托管计费](https://docs.cloudbase.net/run/faq/fee)、[云托管资源与伸缩模型](https://docs.cloudbase.net/run/introduction)。用量数据见[资源基线](../records/2026-11-12-cloudbase-resource-baseline.md)。

部署依据：[CloudBase 官方入口](https://github.com/TencentCloudBase/cloudbase-skills/blob/main/skills/cloudbase/SKILL.md)、其中的 `cloudrun-development` 和 `cloudbase-cli` 指引，以及 [SQLite WAL 限制](https://sqlite.org/wal.html)。

## 产品入口

MCP、页面编辑器、项目资产和版本历史统一托管在腾讯云。客户端通过 HTTPS 调用远程 MCP，不再依赖用户电脑上的常驻 Python 进程。

原方案采用单台 Linux CVM 或 Lighthouse 运行现有 Docker 容器。项目数据库和数据文件挂载持久卷；COS 保存独立分享副本；SCF 执行到期删除。该方式保留当前 SQLite 和项目目录模型；切换 CloudBase 时按上节先适配持久化。

| 云端组成 | 内容 |
| --- | --- |
| CloudBase CloudRun | MCP HTTP 服务、页面编辑器、版本中心、分享访问网关 |
| PostgreSQL 与 COS | 项目配置、数据、草稿、已保存版本、发布记录与业务文件 |
| 私有 COS | 只读分享网页、数据分片、访问控制和清理记录 |
| SCF | 目标为每 6 小时执行到期、撤销和中断上传的物理清理 |
| 域名和 HTTPS | MCP 与网页的统一公开入口 |

现有部署入口见 [自托管服务器](../operations/self-hosted-server.md)，COS 与 SCF 部署见 [腾讯云分享](../operations/self-hosted-server.md#腾讯云在线分享与云端清理)。这是安装自有服务，不是将本地 stdio 配置直接上传到 COS。

## 两类访问密钥

| 类型 | 使用者 | 权限与管理 |
| --- | --- | --- |
| MCP API Key | Agent / MCP 客户端 | 高强度长令牌，经 `Authorization: Bearer` 请求头发送；不作为 URL 参数或页面密钥 |
| 页面分享密钥 | 分享接收者 | 8 位数字，仅访问对应分享；与分享配置绑定，云端保存加盐哈希 |

当前服务端已用 `CHARTS_SERVER_TOKENS` 或令牌文件支持 Bearer 令牌；接入客户端必须支持远程 HTTP MCP 和自定义请求头。首期这些令牌都是服务管理权限，不将它描述为已实现项目级权限、OAuth 或用户账号体系。

API Key 更新采用先同时接受新旧值、更新客户端、再撤销旧值的顺序。MCP 客户端使用专用 API Key 连接管理接口；8 位页面密钥仅供页面访问，腾讯云 SecretId/SecretKey 由云端运行环境管理。

分享密钥产品目标（当前替换方式见下节，独立重置密钥与原链接更新尚未实现）：

1. 每次新建分享生成独立密钥，不从全局部署环境读取固定页面密码。
2. 更新已有分享的目标版本或访问设置时，为该分享生成新密钥；也提供单独的“重新生成密钥”动作。
3. 轮换时递增分享授权代次并更新密码哈希。所有旧会话失效，每个文件请求都检查代次。
4. 保存草稿、保存版本不轮换分享密钥。页面发布与“更新哪些分享”在发布确认中明确列出。
5. 新建分享不会自动撤销同一页面的其他独立分享。撤销或更新操作只作用于选定的分享。
6. 8 位数字密钥不可回读；遗失后生成新密钥。有效期由具体分享控制，支持不过期、7 天和 30 天。

## 保存与发布

下表保留完整产品目标。当前已实现保存检查点、正式发布、恢复草稿、发布记录和固定版本分享；分享更新通过新链接替换旧链接完成，尚无发布时批量选择分享。

| 对象/动作 | 作用 | 是否改变接收者正在访问的内容 |
| --- | --- | --- |
| 草稿 | 保存当前编辑进度与并发版本号 | 否 |
| 保存版本 | 完整校验后创建可命名、可预览、可比较的不可变版本 | 否 |
| 发布版本 | 指定一个已保存版本作为页面当前正式版本，记录发布事件 | 只有在同次发布中选定要更新的分享才改变这些分享 |
| 更新分享 | 将选定分享切到指定发布版本，更新有效期并轮换密钥 | 是；旧会话失效 |
| 恢复为草稿 | 将历史内容复制为新草稿，保留旧历史和当前发布状态 | 否 |
| 回退发布 | 把一个历史已保存版本作为新的发布事件，明确选定要更新的分享 | 是；完成后才替换对应线上内容 |

发布确认应列出版本、变更摘要、目标分享、有效期，以及密钥将轮换的影响。新产物完整上传并通过检查后再切换版本和授权代次；失败保留原发布内容及原有有效授权。不能先让旧分享失效，再开始上传新内容。

每个分享保存明确的发布版本及数据版本引用。编辑草稿或查看历史不能让分享悄悄切换数据。被版本历史引用的数据不因某个分享到期而删除；到期清理只删除该分享专属的远程副本和访问记录。

## 统一版本中心

当前入口为页面顶部“版本与分享”侧栏，包含版本和分享两个标签页；提供命名保存、历史内容摘要、恢复草稿、发布、分享创建、替换和撤销。完整历史图表预览、版本差异比较、独立重置分享密钥仍属后续目标。下列详细交互记录产品目标。

页面顶部集中显示“保存版本”“发布”“版本与分享”。“版本与分享”打开同一侧栏；不再把恢复、发布状态和分享有效期分散在多个菜单中。

侧栏有“版本”和“分享”两个标签页，默认定位当前页面。

版本标签页：

- 按时间显示草稿、已保存版本和发布事件。
- 展示版本名称、时间、变更说明，以及“当前草稿”“已保存”“当前发布”等状态。
- 选择版本时先只读预览，不立即恢复；明确标识正在看历史内容。
- 提供命名、与当前版本比较、恢复为草稿、发布此版本。
- 区分“恢复编辑内容”和“回退线上发布”；前者不影响接收者。
- 没有编辑变化时不重复保存相同版本。保存、发布和恢复结果重新读取确认。

分享标签页：

- 列出分享名称或 ID、目标版本、有效期、访问状态和清理状态。
- 提供复制链接、新建分享、更新分享、重新生成密钥和撤销。
- 新生成的密钥仅在本次操作结果中展示；后续不提供明文查询。
- 已到期显示“已到期”；物理删除完成前显示“等待清理”或“清理重试中”。

## 当前实现与后续目标

- 发布状态与历史保护属性分离；每个页面只有一个当前正式版本，发布事件单独保存。
- 历史恢复只创建新草稿，不自动保存检查点或改变正式发布。
- 版本中心支持只读内容摘要；完整图表历史预览和版本差异比较尚未实现。
- 分享替换先上传当前正式版本的新副本，再撤销选定旧分享；生成新 URL 和新的 8 位密钥，旧会话失效，其他独立分享保持有效。
- 新副本上传失败时保留旧分享。新副本成功但撤销旧分享失败时，返回新链接、密钥和明确的后续撤销动作，避免用户丢失新凭据。
- 原链接上的原子版本切换、单独重置密钥、发布时批量更新分享仍属后续目标。

## 原 CVM / Lighthouse 安装顺序

1. 确定地域、已有或新建 Linux 实例、HTTPS 域名、私有 COS 桶及 SCF 执行角色。
2. 将本仓源码或构建镜像部署到实例；使用现有 `deploy/docker-compose.yml` 挂载 `/data` 持久卷。
3. 在部署环境配置 `CHARTS_PUBLIC_URL`、MCP API Key、COS 地域/桶/前缀和运行凭据。真实密钥不进入源码、页面或文档。
4. 按 `deploy/nginx.conf` 配置 HTTPS 和 Streamable HTTP 转发；MCP 请求不缓冲。
5. 部署 SCF 函数包、启用定时触发，并确认一次成功清理状态。
6. 有既有本地项目时显式迁移项目资产和数据；安装服务后单独执行上传。
7. 客户端改连统一 HTTPS `/mcp`，用 Bearer API Key 鉴权。远程 `projectRoot` 使用服务器项目名。
8. 验证创建/保存/发布/版本恢复、密钥轮换、过期清理和容器重启后的资产保留；退出本地 MCP 后复查云端访问与清理。

服务器端现有启动命令，在项目目录、部署环境和域名配置完成后执行：

```sh
docker compose -f deploy/docker-compose.yml up -d --build
```

## 实施顺序

以下实施步骤已执行，最终验证集中在整理完成后完成。详细结果与未实现的产品目标分别记录，后续无需重跑本轮已通过且未受新改动影响的检查。

1. **完成 CloudBase 存储适配。** PostgreSQL 保存项目、草稿、版本、发布引用、批注、编辑批次和撤销状态；不可变数据版本按 JSON 行分块保存在 PostgreSQL；私有对象存储保存业务文件、导出和分享副本。本地目录仅作可重建缓存。逐项处理现有 SQLite 查询及自定义函数的兼容性，不能只迁移看板 JSON 就宣称完成。远程工具使用云端项目与已上传数据，不能直接读取客户端电脑路径。
2. **完成产品版本流程。** 保留当前工具能力，增加独立的保存版本、发布、恢复为草稿及发布记录；统一版本中心。分享绑定明确版本，更新指定分享时轮换密钥并使旧会话失效。不同分享彼此独立。
3. **完成云端分享与清理。** 配置私有存储和 SCF 定时触发，先验证清理心跳，再开放发布。到期立即拒绝访问，云函数异步删除该分享专属副本及对象历史版本。项目原稿和版本历史不随分享过期删除；用户已下载的文件无法从云端撤回。
4. **通过 CLI 部署并验收候选版本。** 检查构建与启动结果、远程 MCP、API Key 拒绝未授权访问、数据导入与查询、导出、保存/发布/恢复，以及实例更换后的数据保留。验证本地退出后云端清理仍运行。首期沿用单实例上限，容量调整以实际测量为依据。
5. **切换并保留回退路径。** 所有必要检查通过后再把流量切到新版本。旧 `003` 使用本地存储，仅作为服务故障回退；PostgreSQL 业务状态需要同存储后端读取。开始写入新业务数据后，应优先向前修复或部署同存储后端的修复版本。记录客户端 `/mcp` 配置、部署版本和验证结果。

CloudRun 承载 MCP、编辑器和分享鉴权网关；静态网站托管仅用于公开静态资源，不作为受密钥保护的业务副本入口。容器部署版本（例如 `003`、`004`）与用户页面的保存版本、发布记录是不同对象。

### 问题与目标

本轮用户提供的编辑页面 HAR 中，23 个候选索引和数据分片请求覆盖约 22 秒。单个请求等待首字节约 2.48–6.48 秒，接收内容约 1–26 毫秒。HAR 只能定位到等待响应阶段，尚不能区分 PostgreSQL HTTP 网关、COS、服务调度和客户端网络分别占用的时间。当前源码与该次线上部署尚未逐项匹配。

此次 HAR 对应的文件读取路径逐个检查权限、读取看板文档和对象登记，再从缓存或 COS 获取内容。签名编辑链接的撤销检查包含同步数据库访问。批注提交先读最新列表，再整体替换，并通过数据库中的比较和事务保护防止覆盖；冲突保留输入，但没有自动重试。结合对应部署版本及筛选盘点记录判断问题是否仍然存在。

目标：

- 首次打开当前页面时集中准备页面配置、全部选择型筛选器候选项和当前页面可用的业务数据；展示明确的准备状态，准备完成后使用本地数据交互。
- 减少每个文件重复访问 PostgreSQL 的开销。读取缓存与提交修改采用不同的处理方式，用户提交立即检查并保存。
- 四五个浏览器可以同时新增批注或回复；不同批注互不阻塞，同一正文的并发修改需要明确处理。
- 更新批注时保留输入、筛选、滚动位置和正在编辑的页面内容。

| 版本 | 用户可见结果 | 实施内容 | 完成条件 |

| 第一版：集中加载 | 首次准备好候选项和页面数据，后续展开筛选、搜索、排序及重复切换已加载范围无需再次等待相同资源 | 合并启动读取；批量取得版本与对象登记、候选项；复用不可变文件和解析结果；对业务分片采用批量读取，避免逐文件重读文档与登记；把阻塞的云端调用移出异步请求处理线程 | 同一版本候选项完整；每个唯一数据资源在正常加载范围内只下载一次；PG 查询次数不再随每个小文件重复增长；已有链接、权限与版本隔离保持有效 |
| 第二版：并发批注 | 四五人同时新增批注、追加回复均可保存，无需刷新页面或人工处理整表冲突 | 新增按条操作：新增、修改、删除批注，追加回复、修改解决状态与位置；事务内检查权限和目标版本；同一操作重复提交不产生重复内容；客户端使用保存响应更新本人的批注 | 五个独立客户端并发新增、回复和修改不同批注全部保留；新增和回复不先请求最新列表；同一正文冲突明确提示；响应丢失后重试不重复；目标被删除时保留未提交输入 |
| 第三版：独立更新检查（后续项，参数待定） | 页面能检查设计和数据更新，个人输入与编辑不被覆盖 | 分别跟踪设计、数据和批注的变化；合并轻量状态查询；只读取发生变化的内容；页面不可见时暂停轮询，重新可见时检查；跨浏览器批注同步方式另行确定 | 批注变化不触发业务数据下载；多人输入不被同步覆盖；无变化时只读取小型状态；历史预览和固定版本内容不自动切到最新版本 |

本次优先交付第一版和第二版，两者可独立验收。第三版是后续项。第二版提供保存结果和批注变更标识，第三版再确定变更读取能力、定时调度和设计、数据更新提示。

### 第一版的实现边界

- 集中准备当前授权页面使用的数据。候选数据完整加载后，再按界面页码展示。
- 优先复用已有数据目录、Worker、缓存和请求取消机制；不另建一套查询引擎。已加载的数据及候选项继续支持搜索和界面分页。
- 在同一次授权读取批次中复用权限结果、看板版本和对象登记。后续读取批次、保存操作及定时检查仍执行权限检查，沿用 COS 私有访问和现有撤销生效规则。
- 实施前量出当前页面压缩体积、解压后体积和浏览器内存占用。若全量预加载超出实际可承受范围，提出具体页面与测量结果，再确定范围；不静默改回用户打开筛选器时才加载候选。
- 记录初始化、权限、PG 网关、COS、缓存命中与传输的分段耗时。只记录操作类型、次数、时间和字节，不记录凭据、批注正文或业务行。
- 首次与已缓存场景分别测量，依据结果计算提速幅度并决定后续措施。

### 第二版的冲突与兼容规则

服务器维护一份共享批注状态，每条批注和回复具有稳定 ID。新增及回复使用独立操作 ID，数据库在事务中处理重复提交；修改正文携带该条批注的比较版本，以目标内容版本判断冲突。

| 情况 | 处理 |
| --- | --- |
| 不同浏览器同时新增批注 | 全部追加，保留各自 ID |
| 同时回复同一条批注 | 全部追加；同一回复重试只保存一次 |
| 修改不同批注 | 分别保存，避免整表冲突 |
| 同时修改同一段批注正文 | 拒绝过期修改，显示最新内容并保留本人的输入 |
| 删除与修改、回复同时发生 | 以事务检查结果决定；目标已删除时提示并保留输入 |
| 批注与布局修改同时发生 | 分开保存；设计操作保留最新批注，批注操作保留页面设计 |
| 关联组件已删除或位置不能匹配 | 保留批注内容，提示位置失效 |

用户已选择直接追加方式：新增批注或回复时，客户端只发送本次新增内容及稳定操作 ID，服务器在一次事务中追加并返回保存结果。客户端直接提交本次操作，再将保存结果合入当前状态，保留页面位置及其他未提交输入。

网络失败需要区分未提交与结果未知；使用同一操作 ID 重试或读取确认结果。重试以操作收据去重。同一正文冲突由用户检查最新内容后重新提交。正常并发新增通过服务端事务直接追加。

保留现有批注、回复、锚点、解决状态和草稿。旧 `set_annotations` 调用继续保持整表比较保护，新操作返回与现有文档和 MCP 读取兼容的批注表示。数据库迁移先兼容旧服务，再接入新客户端；项目本地存储与云端存储都需实现对应语义。升级本身不创建业务设计版本。

### 第三版的同步规则与待定参数

- 轻量状态检查返回权限状态及设计、数据、批注的变更标识；没有变化时不拉取完整文档或数据分片。
- 批注同步更新列表，保留新批注草稿、回复草稿和正在修改的正文；目标被修改或删除时显示提示，将最新正文与本人的输入分开展示。
- 页面设计或业务数据变化时，编辑页面存在未保存内容则提示用户处理；查看页面按已确定的版本选择规则刷新，继续读取已保存版本。
- 第二版直接保存批注。其他浏览器在进入批注模式、返回标签页时读取最新列表。实时同步和在线成员展示属于后续功能。
- 页面设计和数据的定时检查间隔尚未确认。第三版实施前确定检查频率及跨浏览器批注同步方式，接口应合并所需状态，避免每个字段单独查询。
- 后台标签页暂停定时检查，返回前台检查。避免重复定时器、请求重叠及旧响应覆盖新版本。

### 局部验证与交付顺序

1. 对照目标线上版本记录当前 HAR 基线，补充服务端分段计时与 PG/COS 调用次数；通过当前任务允许的只读方式采集，不将工作区代码当成线上事实。
2. 第一版验证初始化、批量资源授权、缓存复用、候选完整性、取消与版本切换。基于同一页面、版本、网络及筛选条件比较首次加载与重复操作。
3. 第二版验证数据库事务中的五客户端并发，不只测试前端模拟；覆盖重复提交、同条冲突、删除竞争和批注与设计同时保存。本地与云端适配分别检查。
4. 第三版验证同步调度、后台暂停、草稿保留、不同类型版本变化及固定版本读取。五浏览器真实验收用于检查交互效果，不能用单进程模拟替代。
5. 每版只运行直接受影响的局部测试；新增或修改用例维护 `@wu-test` 标记。本地或主动触发 CI 全量测试、浏览器自动化、生产迁移与部署按当前任务授权执行，本计划不视为已获得这些授权。
6. 先部署兼容的数据库与后端，再交付客户端资源；逐项确认源码、构建、数据库迁移和线上运行版本。保留原项目、页面、历史、地址、凭据及有效期。每版完成后在对应现行说明中更新实际行为，证据进入 `docs/records/`。
