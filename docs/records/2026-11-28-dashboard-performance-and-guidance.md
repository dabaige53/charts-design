记录日期：2026-11-28（Asia/Shanghai）。

基线为 `7f614058816c50fd1891b7d2c3a334e7adcd1369`，即合并 PR #24 后的主分支；包含之前的列式交付、本机工作区与独立分享。此次从该提交创建独立工作树。原工作树保持原分支，未覆盖其内容。

## 问题与改动

### 查看与数据预览

- 静态查询在候选项翻页时重复扫描原始数据、去重和排序。现在按不可变输入身份复用候选集合与最近一次搜索结果；连续翻页仅取对应页。字段、来源数组或文件变化使用新身份，返回页与缓存隔离。
- 新增候选缓存最多保留 16 组来源，采用 8 MiB 的保守估算预算，计入字符串及数组引用。超过预算仍完整计算和返回，不抽样。该预算只覆盖新增候选缓存，不代表原始数据、其他查询缓存或整个 Worker 的内存上限。
- 表格排序此前在每次比较中重建字段类型和 raw 字段映射；文本搜索在每行重建可见字段列表。现在分别移到排序、搜索开始前。
- 本地候选搜索通过有界探测选择执行顺序；重复标签先去重再搜索，较多唯一值保留先搜索再分组。探测仅选择计划，全部返回值和总数仍从完整数据计算。探测最多读取 4096 行，保留的不同值按 512 KiB 估算预算限制。
- 本地分组明细在一次聚合中取得当前页与精确总数。超出最后一页时保留独立计数，保证页码修正仍有准确总数。
- 静态候选请求与服务端保持相同的搜索长度和分页范围约束，界面搜索框同步限制到 1000 个字符。

已有的可见组件渐进取数、四路有界请求、Worker 计算和迟到响应隔离继续使用。可见性控制的是数据查询激活，不等同于整页 DOM 虚拟化。

### 制作与保存

渐进编辑器正常保存从四次工具往返改为两次：`dashboard_submit` 后读取一次 `dashboard_get`。服务端仍检查全部组件并保存检查点。HTTP 失败回执和 MCP 的 `DOCTOR_FAILED` 都保留草稿修订，检查失败不会成为已保存版本。

已确认写入但回读失败时，下一次点击先恢复最新草稿并结束旧布局编辑，不重新提交原操作。恢复期间出现其他作者的新修订也不被覆盖。明确的操作拒绝仍保留编辑；过时的保存尝试不会让后续新编辑误入恢复流程。

### MCP 发现与推荐

- `chart_declarations` 保留原单个 `code`，新增 1–8 个唯一 `codes` 批量选择；共享定义只返回一次。
- 40 种图表与 16 种 KPI 都提供各自可执行的合成示例。组件 ID 包含具体代码，可以组合成一个批次；数据与来源保留 fixture 标记。
- 声明发现缓存不可变 JSON，并按安装源文件标识隔离、失效。每次调用返回独立对象。
- `chart_recommend` 支持 `requiresFilterBinding`，返回数据要求、注意事项、绑定方式、结构适配与阅读密度差异。未知指标数量不默认为 1；没有日期类型不等于没有合法的字符串时间轴。
- 有结构适配的候选优先显示，返回状态以实际给出的候选计算。需要相关系数时，不把动态热力图当作能自动计算相关性的实现。
- 图表重复使用不再扣分。直接比较的组件优先保持相同图形、尺度与语义颜色。

### Skills 与设计判断

两个 Skill 分别维护看板、报告流程，共用交付约定。新建、修改与外部迁移有各自入口；工具发现、案例和完整合同按需读取。相关操作一次提交，计算结果与证据按组件批量读取，明细使用显式小页。

选图引导覆盖规模排名、时间趋势、两期变化、目标、构成、分布、关系、流程/留存、变化分解、层级和预测，分别说明需要哪些数据证据及如何避免误用。取消 KPI 形态数量和跨页变化的机械要求，强调阅读层级、比较一致性与信息用途。

同时补齐 live SQL 与快照的生命周期说明、静态分享边界、报告正文不会随读者筛选自动重算的限制，并清理目录与解释中已被 KPI 校验禁止的 `note`、`rankSub` 指导。

## 实测结果

完整原始样本、环境与源码 SHA256 保存在[性能原始数据](2026-11-28-performance-samples.json)。候选源码以内容哈希标识，测量时尚未提交；报告中的 `workingTreeHead` 是其起点，不能替代候选源码哈希。

### 本地查询

Linux x64，Python 3.11.16，SQLite 3.53.1。100 万合成行、1000 个分组，5 次样本的中位数。新旧代码在同一进程中交替测量，读取同一个不可变 SQLite 文件；每次使用空的应用查询缓存，操作系统文件缓存没有清空。

| 查询 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 重复候选搜索并读取一页 | 353.697 ms | 230.908 ms |
| 分组明细首屏及精确总数 | 675.648 ms | 339.828 ms |
| 10 万唯一候选搜索不存在的值 | 33.103 ms | 37.203 ms |

每个样本的返回页、总数、合计与比例均与独立按源行累计的结果核对。该测量不包含数据导入、HTTP、网络、页面绘制。

高基数、稀疏匹配场景仍有约 4.1 ms 的探测开销，因此不能声明每一种候选搜索都更快。独立审查发现无条件先分组会在这一场景重复构建完整唯一集合，最终实现保留了先搜索再分组的执行路径。探测可能因前段数据分布选择较慢的计划，但不会漏掉后续候选或改变计数；测试覆盖重复前缀、全唯一前缀和超长字符串。

### 静态网页查询

Linux x64，Bun 1.3.8。100 万已解码合成行、10 万个唯一候选，每页 10 条。新旧实现各在独立进程运行 3 次；每轮新建查询器，后续页复用该轮缓存。

| 查询 | 修改前中位数 | 修改后中位数 |
| --- | ---: | ---: |
| 首次数值排序 | 1862.514 ms | 616.470 ms |
| 候选项第一页 | 445.530 ms | 328.583 ms |
| 候选项下一页 | 419.434 ms | 0.223 ms |
| 新条件候选搜索 | 377.021 ms | 138.772 ms |
| 同一搜索下一页 | 361.531 ms | 0.124 ms |

缓存后的翻页与首次查询是不同场景。此处不包含网络、Parquet 解码、DOM 或图表绘制，也不代表真实用户端到端延迟。原始报告保留进程最大 RSS；它包括合成数据、运行时及全部测量，不能当作新增缓存的内存大小或生产承诺。

### 声明发现与调用次数

Python 3.11.16。基线和候选使用各自源码包与独立进程，每个场景先记录首次调用、额外预热一次，再测量 7 组，每组 100 次。表中是各组每调用耗时的中位数。

| 调用 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 声明索引 | 1.689380 ms | 0.044263 ms |
| `c02` 声明 | 2.107519 ms | 0.190337 ms |

改后 `c02` 还增加了完整示例。首次调用并非同等程度的冷启动，前面的场景可能已加载共享依赖，因此只在原始报告保留，不用于加速结论。上述微基准不包含进程启动、模型生成、HTTP、网络和宿主时间，不能推导整体制作速度提高相同比例。

对 `c02 / t01 / mc03 / mc14`，在改后同一版本中逐个读取合计 124,812 字节紧凑 JSON；批量读取为 44,639 字节，减少 64.24%，工具调用从 4 次变为 1 次。基线逐个读取为 120,334 字节，内容较少；不将其误写为改后四个完整示例的大小。

推荐器增加证据和适配说明后，每调用中位耗时从 0.117813 ms 到 0.143501 ms，返回 JSON 从 1,283 到 4,055 字节。该项提高的是指导完整性，没有宣称计算加速。
